# Threat-to-test traceability matrix

This matrix traces every case in the [Phase 0 threat taxonomy](threat-taxonomy.md) to the controls and
automated evidence that exist in this repository. It describes the current pre-alpha implementation,
not the complete architecture proposed in the [design](design.md). The deployment boundary and
non-claims in [SECURITY.md](../SECURITY.md) remain controlling.

## How to read this matrix

Control tags distinguish four different effects:

- **P — prevention:** rejects an operation before it receives authority.
- **D — detection:** identifies a bad or inconsistent state; detection alone does not stop a process.
- **C — containment:** latches freeze state or terminates a supervised process after a trigger.
- **E — evidence:** preserves or verifies material for later reconstruction.

Coverage strength is deliberately attack-specific:

- **Strong:** an automated test exercises the case's material attack mechanism end to end within the
  documented boundary.
- **Partial:** tests exercise a material slice of the case, but important mechanisms remain uncovered.
- **Weak:** only generic integrity or containment machinery is relevant; no attack-representative test
  exists.
- **None:** no implemented automated control addresses the case's defining mechanism.
- **Context:** the taxonomy row is a capability trend, not an attack case; it is traced to the missing
  control it motivates rather than assigned attack coverage.

A component can be strong at its narrow property while the case remains partial or weak. In
particular, hash chains detect mutation only when a surviving trusted head is available, local signed
receipts are not independent retention, and the POSIX supervisor is not a hostile sandbox.

## Compact coverage summary

### By taxonomy case

| Strength | Cases | Count |
|---|---|---:|
| Strong | — | 0 |
| Partial | C04, C05, C06 | 3 |
| Weak | C01, C07, C10 | 3 |
| None | C02, C03, C08, C09, C12, C13 | 6 |
| Context | C11 | 1 |

The strongest implemented property is **evidence integrity around one prime-rl policy-promotion
boundary**: content-addressed staging, hash-chain verification, optional signed-head receipts,
single-use Gate authorization, exact approved-path loading, fail-closed outcomes, and bounded CPU
process-group containment. That is meaningful F5 coverage, but it is not general F5 prevention and it
does not imply event completeness.

## Priorities

1. **Close the containment boundary before stronger claims:** add protected credentials, cgroup or
   service-manager termination, OS ownership for freeze/governance state, and live hostile-child tests.
2. **Implement independent, complete telemetry reconciliation:** an external Watchtower should compare
   intercepted actions/resource use with Ledger events, including omission, monitor-kill, egress, and
   joint rollback scenarios.
3. **Build T-BEH for F2/F6 and human-facing F4 tests:** context-labelled paired probes, independent
   administration/model domain, immutable decision packets, and two-person irreversible-action gates.
4. **Make F1 evidence semantic:** shadow-evaluate candidate weights with isolated, held-out/rotating
   evals; bind evaluator code/config/results; test reward gaming rather than only byte substitution.
5. **Instrument F3 and parallel writers:** Ledgered coordination leases plus sequence/duplicate
   analytics and deterministic SELF-001-style regressions.
6. **Add T-RES and T-CAP:** enforced compute/network/topology budgets and signed capability thresholds,
   each wired to a tested freeze path.
7. **Publish only measured adversarial results:** report denominators, false positives, misses,
   deployment assumptions, and exact commits; do not generalize the bounded accepted two-A6000
   topology to capability-tripwire coverage or production safety.
